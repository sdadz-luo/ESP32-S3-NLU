任务与通信

五个任务全部绑定 Core 1（WiFi / lwIP / 定时器在 Core 0，物理隔离），优先级集中在 3~8， 把 9~17 留给后续扩展。所有队列满时都选择丢弃并告警，绝不阻塞输入方。

任务优先级栈阻塞点
task_rhythm83072 Brhythm_q 超时到点翻转
task_key63072 BvTaskDelay(20 ms) + 10 ms 去抖
task_nlu58192 Bcmd_q 永久阻塞
task_serial43072 Bfgets(stdin)
task_display34096 Bui_q 超时 200 ms
队列深度方向满载策略
cmd_q8输入层 → 理解层丢弃 + 日志
rhythm_q4工具层 → 节奏任务返回错误码
ui_q4响应层 / 按键 → 显示任务丢弃 + 告警
为什么节奏引擎用「超时阻塞」而不是定时器？ 每轮循环取两路中最近的翻转时刻，把「到 deadline 的剩余时间」作为 xQueueReceive 的超时—— 收到命令能立刻打断（亚毫秒级），翻转时刻以旧值累加，长期运行也没有累积漂移。

工程结构

components/ 采用 ESP-IDF 的「目录即组件」模式——目录内含 CMakeLists.txt 时， 构建系统把目录自身注册为一个组件、不再扫描子目录，所以二十多个源文件全部平铺。标 入库 的生成文件是固件的编译输入，与源码一一对应。

模块与接口

components/ · 21 个模块

下面按层列出每个模块的职责、对外接口与设计取舍。接口是模块之间唯一的约定—— 改实现不改接口，调用方就无需知情；这在本工程里被反复验证（规则换模型时只动了 nlu.c 内部）。

启动与骨架做最少的事：把硬件、队列、任务按正确顺序立起来

app.c / app.h 启动序列

main 调用的启动面：硬件初始化、队列创建、任务创建。三件事分开成三个函数，是因为它们的时序约束不同。

app.h
void app_hw_init(void);     /* LED / IIC / XL9555 / SPI-LCD（顺序敏感） */
void app_queues_init(void); /* cmd_q 深度 8 · rhythm_q 深度 4 */
void app_tasks_start(void); /* rhythm → nlu → key → serial → display */
  • 初始化顺序有硬约束：xl9555_init 在前、lcd_init 在后——GPIO40 复用了 XL9555 中断与 LCD 的 DC 脚，后者会把引脚从输入改配为输出。
  • 上电自检读一次 XL9555 输入寄存器验证 I2C 通路，再让 LED 亮 300 ms、蜂鸣器短鸣 150 ms 做视觉点验——硬件问题在启动日志里就能看见。
  • 先建消费者、后建生产者：节奏任务是执行汇点、理解任务是命令消费者，先于输入任务创建，任何首次投递发生时下游都已存在。
  • 任务栈不是拍脑袋定的：全部用 uxTaskGetStackHighWaterMark 实测校准，要求余量 ≥ 500 B；task_nlu 因 TFLM 调用链从 4096 加到 8192。
app_types.h 公共类型

全工程的类型词典：设备模式、意图、队列元素。它保证了三方的顺序一致——模型输出的类别索引、语料标签、日志里打印的名字，用的是同一套枚举序。

app_types.h
typedef enum { LED_OFF, LED_ON, LED_BLINK } led_mode_t;      /* BLINK = 5 Hz */
typedef enum { BEEP_OFF, BEEP_BREATH, BEEP_ALARM } beep_mode_t; /* 0.5 / 2 Hz */
typedef enum { I_UNKNOWN, I_LED_ON, I_LED_OFF, I_LED_BLINK, I_BEEP_BREATH,
               I_BEEP_ALARM, I_BEEP_OFF, I_STOP } intent_t;

typedef struct { char text[128]; uint8_t src; } cmd_msg_t;    /* src 预留 SRC_WIFI */
typedef struct { uint8_t target; uint8_t mode; } rhythm_cmd_t;
  • 意图枚举序 unknown=0 … stop=7 即模型输出的类别序——阶段 5 训练时按同一顺序打标签，阶段 6 的 C 侧直接用索引，不需要名字映射表。
  • cmd_msg_t.src 现在就留好了 WiFi 通道的位置（阶段 7 只加一个生产者，队列元素不变）。
main/main.c 程序入口

只保留启动序列，四行调用；应用代码全部在 components/ 下，入口文件不承载逻辑。

  • app_main 返回后 main 任务自动删除——禁止 while(1) 忙等，会饿死 IDLE0 触发看门狗，这条写进了文件头注释。

输入层把外部的字节流变成队列里的一条命令

input_serial.c 串口输入任务 优先级 4

阻塞在 fgets 上读一行，去掉行尾换行，投进 cmd_q；空行忽略。

  • 读错误或 EOF 时 清标志 + 延迟 100 ms 重试，避免出错后变成忙循环烧 CPU。
  • 队列满时丢弃并告警——输入侧永不阻塞，宁丢一条也不让串口卡住。
input_key.c 按键任务 优先级 6

每 20 ms 扫描一次 XL9555 的按键，投递屏幕命令到 ui_q：KEY0 清屏 / KEY1 下滚 / KEY2 回最新 / KEY3 上滚。

  • 扫描用「按住持续返回键值」模式，任务侧按 150 ms 节流：首按立即响应，之后每档一行，实现长按连滚。
  • 按键不进理解层：它是屏幕控制通道，与自然语言输入语义无关——这条边界是阶段 3 明确下来的（早期按键曾映射调试动作，后来改掉了）。

理解层文本 → 意图：模型优先、规则兜底的双层决策

nlu.c 双层决策与分发 模型优先规则兜底优先级 5

消费 cmd_q，产出意图并调用工具。核心是 decide()：模型的 top-1 置信度 ≥ 阈值就用模型，否则把这句话交给关键词规则再试一次，规则也判不出来才是拒识。

nlu.c
#define NLU_CONF_THRESHOLD  0.70f   /* test 集扫描最优区间 0.45~0.75，取上部 */

static intent_t decide(const char *text, bool *by_model, float *conf_out)
{
    if (nlu_model_predict(text, &m_intent, &conf) == ESP_OK) {
        if (conf >= NLU_CONF_THRESHOLD) { *by_model = true; return (intent_t)m_intent; }
    }
    return nlu_understand(text);   /* 规则兜底 */
}
  • 为什么阈值取 0.70 而不是扫描最优的区间中点：区间内准确率无差异，取区间上部更保守——边界置信度的句子交给规则，两套判据都拿不准时落拒识，宁可拒识不可误动作。
  • 关键词规则是 10 条按序 strstr 的优先级判断（UTF-8 子串匹配天然安全），词池与 tools/rule_baseline.py 是同一份数据的两个副本，改一处必须同步另一处。
  • 日志带判定来源："开灯" -> led_on (model 0.98) 或 (rule, model 0.65) 或 (rule)——阈值分析的原始数据就是这些行。
  • 模型初始化失败时永久降级纯规则并打告警，功能可用性不受影响（这条降级路径被专门构造验证过：把 arena 缩到 1 KB 触发 AllocateTensors 失败）。
nlu_model.cc / .h 模型侧：tokenizer + TFLM C++ / TFLM

把一句 UTF-8 文本变成 22 个 token id，交给 TFLite Micro 解释器，返回意图索引与置信度。全工程只有这一个文件用 C++（TFLM 的类接口），对外暴露 C 链接。

nlu_model.h
esp_err_t nlu_model_init(void);   /* 建 resolver / interpreter、分配张量 */
esp_err_t nlu_model_predict(const char *text, int *intent, float *confidence);
  • tokenizer 与训练侧同规则（tools/nlu_data.py）：UTF-8 逐字符解码 → 线性查词表（373 项，微秒级）→ 词表外字符跳过 → 补 <pad> 到 22。
  • UTF-8 解码逐级短路：遇到 '\0' 立即判失败，不会越界读尾字节——这是手写解码器最容易出错的地方。
  • 使用 静态 tensor arena（16 KB）+ placement new，解释器对象与张量区都不走堆——嵌入式里没有动态分配的余地。
  • 用 MicroMutableOpResolver<9> 精确注册 9 个算子而非 AllOpsResolver，省下大量 flash。

响应层意图 + 实时状态 → 一句像人说的话

resp.c / resp.h 组合式回复

回复不是查表输出固定句，而是「前缀 × 主体 × 跨通道补语 × 后缀」四段随机组合，并且会读取执行层的实时状态填充补语——同一意图连发五次，措辞和状态描述都会变化。

resp.h
void resp_send(const char *text);                       /* 系统消息：串口 + 屏幕 */
void resp_compose(intent_t intent, bool executed, const char *input);
  • 跨通道补语是亮点：命令只作用于一个设备时，若另一设备在工作就补一句——「灯开始闪烁（蜂鸣器仍在报警中）」，提示不会静默丢上下文。
  • 拒识与失败文案不套前后缀：拒识应该像一句直接回应，而不是「好的，抱歉我没听懂，还需要什么吗？」这种奇怪的执行确认腔。
  • 失败路径（命令未送达执行层）按实时状态说明「没有生效」，不谎报成功。
  • 随机源用 esp_random()（硬件 RNG，无需播种）；模板池全部 static const 存 flash，零动态分配。

执行层从意图到电信号：唯一写硬件的通道

tools.c / tools.h 工具函数

意图到硬件的映射层。契约只有一条：只向 rhythm_q 投递命令后立即返回——不阻塞、不碰硬件、不做时序。

tools.h
esp_err_t tool_led_set(led_mode_t mode);
esp_err_t tool_beep_set(beep_mode_t mode);
esp_err_t tool_stop_all(void);   /* LED → OFF，蜂鸣器 → OFF */
  • 新增一个工具 = 新增一个投递函数；调用者（理解层）不需要知道节奏任务怎么实现。阶段 3 接屏幕时，工具层一行未改。
rhythm.c / rhythm.h 节奏任务：节拍引擎 唯一执行者优先级 8

全工程唯一写 XL9555 输出的地方。维护 LED / 蜂鸣器两路 {模式, 下次翻转时刻, 半周期, 当前电平}，在 rhythm_q 上以「到最近 deadline 的剩余时间」为超时阻塞。

  • 收到命令立即应用新模式基态（亚毫秒打断）；超时则对到期通道翻转电平，next_us 以旧值累加——长期运行无累积漂移。
  • 半周期：LED 闪烁 100 ms（5 Hz）、蜂鸣器报警 250 ms（2 Hz）、呼吸 1000 ms（0.5 Hz）。
  • 对外暴露两个状态快照 rhythm_led_mode() / rhythm_beep_mode()：单写者（本任务）+ volatile 单字节读写，读者免锁——响应层和屏幕状态区都靠它。
  • 为什么让执行者持有状态而不是理解层：按键通道绕过理解层直接控制屏幕/工具，且命令在队列里有延迟，只有真正执行的这个任务才知道「实际生效」的模式。
led.c · iic.c · xl9555.c 板级驱动（BSP） 移植自正点原子例程

正点原子配套例程的 BSP 移植：LED（GPIO1，低电平点亮）、I2C0 主机（GPIO41/42，400 kHz）、XL9555 IO 扩展（蜂鸣器 BEEP_IO 写 0 为响，按键在输入寄存器高 4 位）。

  • XL9555 挂 I2C0，输出寄存器只被节奏任务写；按键只读输入寄存器——两者寄存器不同、单笔事务有驱动锁，交错无害。
  • BSP 使用 legacy I2C 驱动（IDF v6.1 已弃用、v7.0 移除）——这是有意识的接受项，学习工程不为迁移成本买单，已记录在案。

font16.c / font16.h 中文字库

16×16 点阵字库，以原始块形式存放在 flash 的 storage 分区（偏移 0），固件用 esp_partition_read 直读——无文件系统开销，也不需要挂载。

  • 字库格式（NLUF）：16 字节头 + 区间表 + 字模数据；覆盖 CJK 基本区等三段共约 2.1 万字、660 KB，保证任意用户输入都能显示。

模型结构：字符级 TextCNN

tools/train_textcnn.py

32,104 个参数、43.3 KB 的 int8 模型，在 ESP32-S3 上完成 8 类意图分类。 结构本身是教科书式的文本分类网络，值得说的是每一处选择的理由——以及一个被 TFLM 算子集倒逼的改动。

01
为什么是字符级而不是词级
中文分词在端侧意味着额外的词典或模型，而字符级把词表压到 373 个字符—— 表小、模型小，新词天然由已有字组合覆盖，没有 OOV 的额外代价。
02
为什么三路不同卷积核
k=2/3/4 分别看 2、3、4 个字，覆盖「开灯」「点个灯」「别亮着了」这类不同长度的句式； 三路并联让模型同时拥有三种粒度的感受野。
03
为什么用全局最大池化
池化取每个通道的峰值，把「模式在哪里出现」抹掉——「请帮我开灯」和「开灯谢谢」 命中同一个模式；同时它让参数量与句长完全解耦。
被 TFLM 的算子集倒逼的一处改动：替代 Keras Embedding

最初用的是标准的 keras.layers.Embedding。转换到 TFLite 后，它的负索引语义 （支持 x[-1] 取最后一行）在计算图里引入了 LESS / ADD / SELECT_V2 三个算子——而 TFLM 的 SELECT_V2 不支持 int32，而 token id 输入恰好就是 int32，于是板端 Invoke() 直接失败。

解决方式是把嵌入层换成裸 tf.gather 的自定义层（nlu_data.CharEmbedding， 训练与量化脚本共用），负索引逻辑消失，算子收敛为 9 种，TFLM 全部支持：

tools/nlu_data.py自定义层（训练 / 量化反序列化共用）
class CharEmbedding(keras.layers.Layer):
    """等价 Keras Embedding，但用裸 tf.gather——避开 TFLM 不支持的 SELECT_V2(int32)。"""
    def build(self, _input_shape):
        self.table = self.add_weight(name="table", shape=(self.vocab_size, self.dim),
                                     initializer="uniform", trainable=True)
    def call(self, x):
        return tf.gather(self.table, x)

最终注册的 9 个算子：GATHER · EXPAND_DIMS · CONV_2D · RESHAPE · REDUCE_MAX · CONCATENATION · FULLY_CONNECTED · SOFTMAX · DEQUANTIZE。 这条经验被完整记录下来，见 docs/STAGE6_DESIGN.md。

量化：从 125 KB 到 43.3 KB，精度零损失

指标float32int8 全整型
权重体积约 125 KB43.3 KB
test 准确率98.9%98.9%
掉点0.00 个百分点（验收标准 ≤ 2）
输入 / 输出int32 [1,22] / float32 [1,8]同左（未显式量化）
  • 全整型量化的含义：权重和激活都是 int8，中间计算在 int32 累加器上做再重缩放—— 对没有硬件 FPU 的单片机，整数运算比浮点快得多，也让 esp-nn 的 SIMD 优化可以介入。
  • 代表数据集从 train 分层抽 300 条（每类都覆盖），绝不使用 test—— 量化校准也必须遵守「test 只考一次」的评估纪律。
  • 输入输出不显式量化：TF 2.21 不接受 int32 作为量化输入类型，而不设置时输入保持 原生 int32（token id 原样进入嵌入表，词表 373 超出 int8 范围），输出保持 float32—— 实测零掉点，且省掉了 C 侧的反量化计算。
  • 模型以 flash rodata 形式编译进固件（nlu_model_data.cc，零拷贝）， 不占 RAM、无需运行时加载与校验——更新模型 = 重跑量化脚本 + 重新构建。

中文字库的文件格式（NLUF）

字库由 tools/gen_font.py 从思源黑体 / Noto Sans SC（SIL OFL 1.1）渲染生成， 16 px 点阵、与 ASCII 的 8×16 字模同高配对。文件只有三段，固件按码点二分查区间、直读字模：

段内容说明
头 16 Bmagic "NLUF" + 版本 + 宽高 + 区间数装载时校验 magic 与几何参数
区间表每区间 { 起码点, 止码点, 数据偏移 }按码点升序，覆盖 CJK 基本区等三段约 2.1 万字
数据区每字 32 B（16×16，行优先，MSB 在左）与 ASCII 字模取模方向一致，渲染代码只有一份
为什么不用 SPIFFS / FAT——字库是一张只读的定长索引表， 挂载文件系统只会带来内存开销与失败面。分区原始块 + esp_partition_read 是零挂载、 零文件句柄、可直接按偏移寻址的最简形态；真正需要多文件时（音频等）再启用 vfs 的 FAT 区。 字库缺失时固件自动降级为占位框，界面不崩。
