# 阶段 2 细化设计：响应层 2.0

本文是《项目路线图》阶段 2 的实施依据：把固定回复升级为「前缀池 × 主体模板 × 后缀池」的组合式回复，并让执行层暴露实时状态供填充。范围与完成标志见 ROADMAP 阶段 2 一节。

> 状态：已完成，2026-10-02 验收通过；词池措辞留待阶段 3 精化。

## 目标与范围

- 执行层暴露设备状态（LED / 蜂鸣器当前模式），供响应层查询
- 响应层模板组合引擎：同一意图多次执行，回复措辞随机变化且状态描述准确
- 不包含：屏幕（阶段 3）、模型（阶段 4~6）、状态查询意图（阶段 8 可选）

## 状态暴露（核心决策）

现状：`led_mode` / `beep_mode` 只存在于 `task_rhythm` 的循环局部变量中，响应层不可见。

推荐方案：状态仍由节奏任务持有，在 `rhythm.c` 加两个只读接口——

```c
/* rhythm.h 新增 */
led_mode_t  rhythm_led_mode(void);      /* 读 LED 当前模式快照 */
beep_mode_t rhythm_beep_mode(void);     /* 读蜂鸣器当前模式快照 */
```

- **单写者 = 节奏任务**（收到命令应用新模式时同步更新），读者 = 理解 / 响应层；快照为单字节对齐读写，无锁安全
- 备选：独立 `app_status` 模块集中存状态，阶段 3（LCD 状态区）多一个读者时接口更中立；先不做，阶段 3 需要时再提取
- 为什么不让响应层跟踪意图：按键调试通道绕过理解层直调工具，且命令从投递到生效隔着队列——只有执行者知道「实际生效」的模式

## 回复组合引擎

组装顺序：`[前缀] + 主体（意图 + 目标设备结果描述） + [跨通道补语] + [后缀]`

| 部件 | 内容 | 数量（首版） |
| --- | --- | --- |
| 前缀池 | 「好的，」「收到，」「没问题，」、空串 | 4 |
| 主体模板 | 按意图各一组候选句，如 led_on：「灯已点亮」「灯切换为常亮模式」 | 每意图 3~5 |
| 跨通道补语 | 条件性追加：另一通道非 OFF 时补一句（如「（蜂鸣器仍在报警中）」），否则省略 | 每模式 1 条 |
| 后缀池 | 空串、「还需要什么吗？」「随时吩咐。」 | 3 |

- 随机源：`esp_random()`（硬件 RNG，无需播种；池规模小，取模偏差可忽略）
- 组装：`snprintf` 拼接进栈上 `char[192]`（UTF-8 纯拼接，不做字符切分）
- 失败路径：命令未送达执行层时不谎报，回复引用实时状态（如「命令没送达，灯仍是熄灭状态」）
- 主体 / 前后缀池与组合逻辑全部在 `resp.c`；`resp_for_intent()` 删除

接口草案：

```c
/* resp.h */
void resp_send(const char *text);                  /* 保留：启动语、调试行 */
void resp_compose(intent_t intent, bool executed); /* 组合式回复 */
```

## 状态描述映射

```text
LED_OFF → 熄灭/已关闭   LED_ON → 常亮   LED_BLINK → 5Hz 闪烁
BEEP_OFF → 已停止       BEEP_BREATH → 呼吸提示（0.5Hz）   BEEP_ALARM → 报警（2Hz）
```

## 并发与资源

- 模板池全部 `static const`（存 flash），无动态分配
- 组合缓冲在 `task_nlu` 栈上（栈 4096 B，余量以阶段 1 水位实测为准）
- 状态快照单字节原子，无需临界区

## 实施顺序

1. `rhythm.c/h`：状态更新点 + 两个 getter
2. `resp.c/h`：组合引擎（词池 + 组装 + 失败路径），删除 `resp_for_intent`
3. `nlu.c`：改调 `resp_compose`
4. 构建零告警 → 烧录跑验收清单

## 验收清单

- 同一意图连发 5 次：至少出现 3 种不同措辞组合
- 状态描述准确：LED 命令的回复描述灯的实际状态；蜂鸣器命令的回复在另一通道工作时带补语
- 拒识回复也有 2 种以上变化
- 失败路径以代码走查确认（正常工况 `rhythm_q` 不会满，难以实操触发）
- 阶段 1 验收项无回归；构建零告警
